# 方案 1：分段转录（大化小 + 按视频 ID 缓存 + 定长驻留）

> 状态：**待讨论，未开发**
> 目标：任意长度的视频都能转录，内存占用恒定；同一个视频重跑直接命中缓存。

---

## 1. 要解决什么

现在 `https://www.bilibili.com/video/BV1Sj2aB9EXf/`（黄仁勋播客，148 分 26 秒）跑到一半报错。

实测结论：

| 环节 | 结果 |
|---|---|
| 解析 | ✅ 成功，返回 1 个白名单内地址 |
| 文件 | 86.2 MB，AAC 81 kbps |
| 下载 | ✅ 可行 |
| 解码 | ✅ 可行（86 MB → 148 分钟 PCM） |
| **卡点** | `web/source.mjs` 里 `decoded.duration > 7200` 硬上限 |

单这一条好改，但改完下一个更长的视频还会撞墙。真正的问题是**一次性把整个视频解成 PCM 再切窗口**：

```
下载 86 MB → decodeAudioData(全部) → 1.14 GB AudioBuffer → 570 MB 单声道
                                          ↑ 峰值约 1.7 GB
```

所以要改成：**分段下载 → 分段解码 → 分段转录 → 丢掉这一段的内存。**

## 2. 已验证的技术前提

### 2.1 文件是标准 fMP4（.m4s），可以按片段切开

在浏览器里读前 512 KB 解析出来的结构：

```
ftyp    36 B    @0
moov    794 B   @36         ← 初始化信息（轨道、采样率、编解码器）
sidx    21 KB   @830        ← 片段索引：每个片段的字节数和时长
moof    1968 B  @22246   ┐
mdat    46 KB   @24214   ┘  片段 1
moof    1040 B  @70856   ┐
mdat    61 KB   @71896   ┘  片段 2
...                          每个片段约 50-62 KB
```

### 2.2 `初始化段 + 连续的若干片段` 能独立解码

实测（`new AudioContext({sampleRate:16000})`）：

| 拼接内容 | 结果 |
|---|---|
| `ftyp+moov+sidx`（23.6 KB）+ 2 MB 片段 | ✅ 解码出 **211.8 秒**，576 ms |
| 同上 + 8 MB 片段 | ✅ 解码出 **825.6 秒**，1535 ms |
| 从非 `moof` 边界起切 4 MB | ❌ `EncodingError`（所以必须对齐片段边界） |

**结论：只要每段都从 `moof` 边界开始，并且前面拼上初始化段，就能一段一段解码。**

### 2.3 `sidx` 里有完整的片段表

`sidx` 21 KB / 每条约 12 字节 ≈ 1750 条，对应全片约 1540 个片段（86 MB ÷ 56 KB）。
每条给出：**该片段的字节数 + 该片段对应的时长**。

所以不需要猜边界，也不需要扫描整个文件——只读头部 256 KB 就能拿到全表。

## 3. 核心设计

### 3.1 分三段职责

```
① mp4-segment.mjs   解析 sidx → 片段表 → 按时间分组
② direct-audio.mjs  按分组用 Range 下载，只下当前需要的那几段
③ source.mjs        逐段解码 → 切 24 秒窗口 → 推给队列 → 释放这一段
```

### 3.2 内存模型：只驻留 2 段

设每段 = 5 分钟音频。

| 项 | 计算 | 大小 |
|---|---|---|
| 一段的原始文件 | 5 分钟 × 9.7 KB/s | ≈ 2.9 MB |
| 一段解码后 AudioBuffer（16 kHz 双声道 float32） | 300 × 16000 × 2 × 4 | ≈ 38 MB |
| 一段单声道混音 | 300 × 16000 × 4 | ≈ 19 MB |
| **单段峰值** | | **≈ 57 MB** |
| **驻留 2 段（当前 + 预取下一段）** | | **≈ 115 MB** |

**总驻留与视频长度无关。** 148 分钟的视频和 15 分钟的视频，内存占用一样。

### 3.3 无限转录

因为：
1. 文件按片段流式下载，不用一次性持有 86 MB
2. 每段解码后立刻切窗口入队，然后丢掉这段 PCM
3. ASR 队列自己按 20 分钟做背压（现有逻辑）

所以唯一的上限是**磁盘写缓存的空间**和**用户愿意等多久**，不是内存。

## 4. 缓存设计（只缓存文字）

**原则：缓存的是转录出来的文字，不是下载下来的音频。**
音频每次都重新取（反正分段之后每段才 3 MB），这样缓存体积小、语义清晰、不会因为音频换成文字把空间挤爆。

### 4.1 现状

`web/download.mjs` 的 `openDownloadCache()` 用 IndexedDB 的 `blocks` 一张表同时存两样东西：

- 音轨分块（`downloadAudio` 的断点续传）
- ASR 检查点（`session.mjs` 第 59-66 行）—— 这个是文字

键：`asr:${model}-v2:24-2:${language}:${digest}:${offset}:${keepUntil}`

所以**逐窗口的转录结果其实已经在缓存了**，这就是重跑同一个视频会秒出的原因。
问题在于它和音频分块混在一张表、按 24 小时一刀切、键是音频 digest 而不是视频 ID。

### 4.2 新的表结构

只用一张表 `transcripts`，**只存文字**：

```js
// objectStore: transcripts
{
  key:  "bilibili|BV1Sj2aB9EXf|small|chinese|v1|1234.5",   // windowStart 秒
  text: "2012年10月12日在意大利佛罗伦萨举办的欧洲计算机视觉大会期间…",
  start: 1234.5,
  end: 1264.5,
  model: "small",
  language: "chinese",
  videoId: "BV1Sj2aB9EXf",
  platform: "bilibili",
  title: "黄仁勋首次上乔罗根播客",
  durationSec: 8906,
  sourceFingerprint: 90354405,   // 文件字节数，换源时自动失效
  at: 1792911721000
}
```

**一个 30 秒窗口的文字约 150-250 字节。** 148 分钟的视频约 300 个窗口 → **约 60 KB**。

### 4.3 索引与淘汰

```
index: byVideo   (platform, videoId)   → 便于"这个视频转过没有"、按视频清理
index: byAt      (at)                  → 便于 LRU 淘汰
```

淘汰策略：

| 规则 | 值 |
|---|---|
| 总量上限 | 200 MB（约 3000 个长视频，或者几万个短视频） |
| 淘汰顺序 | 最久未访问的整条视频先删（按 `byVideo` 成组删，不拆散） |
| 单独清理 | 界面上可以「清掉这个视频的缓存」 |
| **不设时间 TTL** | 只要没被挤出预算就一直留着 |

### 4.4 音频分块怎么处理

| 方案 | 说明 |
|---|---|
| **建议：去掉持久化的音频分块缓存** | 分段之后每段才 3 MB，重下很快，没必要占空间 |
| 保留内存中的当前段 | 只活在一次会话里，页面关掉就没了 |

这样 IndexedDB 里**只有文字**，符合「缓存是文字缓存」的定位。

### 4.5 命中后的行为

| 情况 | 行为 |
|---|---|
| 全部窗口命中 | **不解析、不下载、不解码、不加载模型**，直接从 IndexedDB 拼出完整字幕 |
| 部分命中 | 只对缺失的窗口下载+解码+转录，已有的跳过 |
| 全都未命中 | 正常跑完整流程，边跑边写 |

界面显示：

```
已从本机缓存恢复 302 / 300 段，剩余 69 段需要识别。
```

## 5. 处理流程

```
[1] 解析          拿到 { urls, duration, title }                    ~0.4 s
      ↓
[2] 读头部        下载 bytes=0-262143                               ~0.2 s
      ↓
[3] 解析 sidx     得到片段表 [{offset,size,seconds}, ...]            <10 ms
      ↓
[4] 按 5 分钟分组  得到 [{startByte,endByte,expectSeconds}, ...]      <10 ms
      ↓
[5] 查缓存        已有哪些窗口？                                     <50 ms
      ↓
[6] 逐段循环      对每个还需要处理的分组：
      ├─ Range 下载这一段（初始化段 + 该段片段）
      ├─ decodeAudioData → AudioBuffer（≈38 MB）
      ├─ 混成单声道 16 kHz（≈19 MB）
      ├─ windowAudio → 每 24 秒一个窗口
      ├─ 逐个送 ASR 队列（带全局时间偏移）
      ├─ 每个窗口的结果写进 `transcripts` 表
      └─ 释放这一段的所有内存
      ↓
[7] 收尾          等队列跑完，拼出完整字幕
```

第 6 步是**串行**的：下一段要等上一段进了队列才下载。这样峰值就是 2 段。

如果想更快，可以预取下一段（`+1`），峰值 3 段 ≈ 170 MB，仍然很小。

## 7. 边界情况

| 情况 | 处理 |
|---|---|
| 没有 `sidx` | 回退：分块下载并扫描 `moof` 标记，建立偏移表 |
| 片段表解析失败 | 回退到今天的整段模式（受 128 MB / 2 小时限制） |
| 某一段解码失败 | 二分该段重试一次；仍失败就跳过并标记，不整段崩 |
| 视频换源（时长或体积变了） | 缓存键里的 `durationSec`/`fileSize` 变了，自动失效 |
| 中途关页面 | 已完成的窗口都在缓存里，重开从断点继续 |
| 用户中途点停止 | 已转的部分保留并展示，和现在行为一致 |
| 直播回放/无 `duration` | 走整段回退模式 |

## 9. 加速手段（实测）

在 `BV1QAnB67EL3` 上取同一段 120 秒中文音频，对比不同切分方式：

| 配置 | 耗时 | 实时率 | 结论 |
|---|---|---|---|
| **24 秒窗口 ×5（现状）** | 29.6 s | 4.05× | 慢，且末段出幻觉 |
| **30 秒窗口 ×4** | **21.0 s** | **5.71×** | ✅ **采用** |
| 120 秒整段一次 + 内置 `chunk_length_s` | 28.8 s | 4.17× | 没收益 |
| 120 秒一次不带切块 | 5.9 s | 20.2× | 假象，只转了前 30 秒 |
| 2 个 ASR 会话并行 | — | 0.63× | ❌ 更慢 |
| `small` 换 `fp16` | — | 0.30× | ❌ 更慢还出幻觉 |
| `small` 换 `base` | — | 3.4× | 比 30 秒窗口的 small 还慢 |
| `small` 换 `large-v3-turbo` q4 | 10.2 s / 30 s | 2.93× | 更准但慢一倍，见下 |

### turbo 的取舍

`onnx-community/whisper-large-v3-turbo` 在浏览器里跑得通（q4 编码器 + q4 解码器，
加载 57 秒，模型约 400-800 MB），但：

| | small | large-v3-turbo |
|---|---|---|
| 实时率 | **5.71×** | 2.93× |
| 148 分钟视频耗时 | **约 26 分钟** | 约 51 分钟 |
| 识别质量 | `智商比赛`（错） | `这场比赛`（对，还带标点） |

**结论：默认仍然用 small。** 准确度差距交给文章生成那一步的提示词矫正（已经做了）。
turbo 作为「识别设置」里的高档位选项保留，给对准确度敏感的场景用。

### 为什么 30 秒更快

Whisper 的编码器输入**固定 30 秒**，不足会补零。

- 24 秒窗口 → 每段白算 6 秒，浪费 25% 编码算力，还多一次固定开销
- 30 秒窗口 → 刚好不浪费

### 为什么 24 秒还更差

同一段音频，24 秒窗口的末段跑成了幻觉：

```
24s 结尾：拿去拿去拿去拿去拿去…（重复几十次）
30s 结尾：格比较沉默寡言自逼内敛主要原因可能是：他们家在英国有一个比较小众的信仰…
```

24 秒版本 942 字里大半是这些重复垃圾。**30 秒版本 645 字，内容是正常文本。**

所以这不是「用质量换速度」，是两头都赚。

### 结论

**方案里的窗口从 24 秒改成 30 秒**，重叠保持 2 秒。
这让 148 分钟视频的识别时间从约 65 分钟降到约 26 分钟。

### 还没试过的方向

这三个不做进方案 1，但记下来备选：

| 方向 | 预期 | 代价 |
|---|---|---|
| `whisper-large-v3-turbo` | 解码器只有 4 层（large 是 32 层），可能又快又准 | 模型约 800 MB，首次下载重，显存占用高 |
| VAD 跳过静音段 | 讲座类视频能省 5-15% | 需要额外 VAD 模型；播客这种少静音的内容没收益 |
| 用 `tiny` 先定位语音段，只对说话部分跑 `small` | 长静音的视频收益明显 | 两倍模型加载，流程复杂，收益不确定 |

这三个都要先测再决定，不在方案 1 范围里。

## 10. 不做的事

- **不做多 worker 并行**。实测 2 个 ASR 会话跑 4 个窗口：22.1 s → 35.1 s，0.63×，更慢。
- **不换 fp16 精度**。实测 10 秒音频要 28.8 s，还输出幻觉。
- **不引入 mp4box.js 之类的依赖**。sidx 结构足够简单，自己解析约 120 行。
- **不改模型默认值**。保持 whisper-small + q4/q4。

## 11. 已定的参数

按「大部分是长视频」这个前提，参数全部定死，不再问了：

| 项 | 定值 | 理由 |
|---|---|---|
| **窗口长度** | **30 秒**，重叠 2 秒 | 实测 5.71× 且不出幻觉；24 秒会崩 |
| **每段音频** | **5 分钟** | 一段 ≈ 2.9 MB 文件 + 57 MB 内存。148 分钟的视频切 30 段，请求开销可忽略 |
| **驻留段数** | **2 段**（当前 + 预取 1） | 峰值 ≈ 115 MB，与视频长度无关 |
| **转录缓存上限** | **200 MB 文字，LRU 按视频整组淘汰** | 148 分钟才 60 KB，能存几千个 |
| **缓存时间限制** | **无** | 只要没被挤出预算就一直留着 |
| **确认对话框** | 仅 **> 30 分钟** 时弹 | 短视频每次弹太烦 |
| **超长警告** | **> 4 小时** 额外警告一次 | 4 小时要跑约 42 分钟 ASR，防误操作 |
| **音频分块缓存** | **不做持久化** | 每段才 3 MB，重下很快；IndexedDB 只存文字 |
| **并行** | **不做** | 实测 0.63×，更慢 |
| **模型** | **默认 small + q4/q4** | 5.71×；turbo 只有 2.93× |

### 为什么是 5 分钟而不是更长

长视频为主，直觉是「段越大越好」，但段大小只影响两件事：

- **内存**：10 分钟段 = 115 MB/段 × 2 驻留 = 230 MB，翻倍但没必要
- **请求次数**：148 分钟切 5 分钟是 30 次，切 10 分钟是 15 次——都是秒级，没区别

5 分钟是「内存不痛、请求也不痛」的平衡点。

### 还剩一个开放项

**字幕轨和 ASR 结果要不要合并缓存？**
B 站视频如果后来官方加了字幕，缓存里已经有 ASR 结果了——用哪个？

**决定：优先用缓存的 ASR 结果。** 用户已经等到结果了，不要因为平台后来补了字幕就失效。
